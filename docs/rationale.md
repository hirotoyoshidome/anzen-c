# 規約の背景と補足

この文書は、[C言語コーディング規約](c-coding-standard.md) の背景にある考え方と補足知識をまとめたものです。規約として守るべき内容は規約本文を優先してください。

## Cを使う前提

Cは言語仕様が小さく、メモリ配置やポインタを直接扱えるため、低レベル制御や性能が重要な場面で有効です。一方で、文字列、JSON、CSV、Webアプリケーション、ユーザー入力の多いアプリケーション層などは、安全に実装するための負担が大きくなります。

Cには公式のパッケージマネージャがなく、外部ライブラリの導入と管理はプロジェクトごとに設計が必要です。そのため、Cを採用する場合は「Cで実装する理由」が明確であることが望ましいです。

ANZEN-Cは、特定プロジェクトのC実装を置くためのリポジトリではありません。別のCプロジェクトに適用する規約、レビュー観点、将来的なチェック用スクリプトを管理するための場所です。

## 対象環境

この規約は、Linux/POSIX環境だけでなく、組み込み環境も対象にします。特にESP-IDFを使うプロジェクトでは、標準C、GCC、ESP-IDF、FreeRTOS、ターゲット依存APIの境界を意識する必要があります。

同じCコードでも、ホスト環境で動くコードとマイコン上で動くコードでは制約が異なります。組み込み環境では、ヒープ容量、スタック容量、割り込み、タスクスケジューリング、ログ出力の負荷、初期化順序が設計に大きく影響します。

## ヘッダとソース

Cでは、宣言をヘッダファイル、実装をソースファイルに分ける構成が一般的です。ヘッダは利用者に見せるインターフェイスであり、ソースファイルは実装の詳細です。

ヘッダファイルを読み込んだ翻訳単位は、そのヘッダの内容を含めてコンパイルされます。そのため、不要な依存をヘッダに増やすとビルド時間や依存関係が悪化します。

ソースファイルを `#include` すると、同じ実装が複数の翻訳単位に展開され、重複定義や意図しないビルド結果につながります。通常は避けます。

## ポインタの基本

ポインタはメモリ上のアドレスを保持する値です。Cでは、配列、文字列、動的メモリ、構造体の受け渡しなど、多くの場面でポインタを使います。

- `&value` は値のアドレスを得る。
- `*ptr` はポインタが指す値を参照する。
- `struct_ptr->member` は構造体ポインタからメンバへアクセスする。
- `struct_value.member` は構造体の実体からメンバへアクセスする。

ポインタ演算はバイト単位ではなく、ポインタの指す型のサイズ単位で進みます。たとえば `int *` のインクリメントは、通常 `sizeof(int)` バイト分進みます。

## 文字列とエンコーディング

Cの文字列は、末尾にNUL文字を持つ `char` 配列です。文字列の長さとバッファ容量は別の概念です。NUL文字の領域を忘れると、バッファオーバーフローや未定義動作につながります。

UTF-8の日本語文字は複数バイトで表現されるため、`char *` を1バイトずつ進める処理は「1文字ずつの処理」ではありません。`wchar_t` も環境によりサイズや扱う文字集合が異なるため、UTF-16固定の型として扱うべきではありません。

マルチバイト文字列を正しく扱う必要がある場合は、対象エンコーディングと利用ライブラリを明確にしてください。

## スコープと所有権

関数内で宣言した自動変数は、関数の終了後に寿命を失います。そのアドレスを返すと、呼び出し側は無効なポインタを参照することになります。

関数が呼び出し元へデータを返す方法は、主に次のいずれかです。

- 呼び出し元が用意したバッファや構造体へ書き込む。
- 関数内で動的メモリを確保して返す。
- 静的領域のデータを返す。

動的メモリを返す場合は、誰が `free` するのかを必ず明確にします。静的領域のデータを返す場合は、再入性やスレッド安全性に注意が必要です。

## 動的配列

要素数が実行時に変わる配列では、現在の要素数と確保済み容量を分けて管理する方法が一般的です。容量が足りなくなったときだけ `realloc` で拡張すれば、毎回再確保するより効率的です。

`realloc` は新しい領域へ移動することがあります。また、失敗時には `NULL` を返しますが、元の領域は解放されません。そのため、戻り値を直接元のポインタに代入すると、失敗時に元の領域を失う危険があります。

## フレキシブル配列メンバ

フレキシブル配列メンバは、構造体の末尾にサイズ未指定の配列を置く機能です。

```c
typedef struct {
    size_t count;
    int values[];
} IntArray;
```

確保時は、構造体本体のサイズに配列要素分のサイズを加えます。メモリが連続するため効率的ですが、サイズ変更には再確保とコピーが必要になる場合があります。

要素数が頻繁に変わる場合は、ポインタメンバと `count`、`capacity` を持つ設計が扱いやすいことがあります。

## 関数ポインタ

関数ポインタは、関数のシグネチャを値として扱うための仕組みです。コールバック、処理の差し替え、簡単な抽象化に使えます。

```c
typedef int (*CompareFunc)(const void *left, const void *right);
```

関数ポインタは柔軟ですが、過度に使うと制御の流れが追いにくくなります。公開APIで使う場合は、引数、戻り値、呼び出しタイミング、所有権を明確にしてください。

## 抽象化設計の考え方

Cにはクラスやインターフェイス構文はありませんが、抽象化は可能です。公開ヘッダで見せる型と関数を絞り、内部構造をソースファイル側へ隠し、関数ポインタで振る舞いを差し替え、初期化関数と破棄関数で所有権を管理することで、Cでも安全な抽象化を作れます。

抽象化は、コードを飾るためのものではありません。抽象化は制約であり、正しい制約は安全性を高めます。たとえば、内部状態を直接触れないようにする、解放方法を1つに固定する、呼び出し順序をAPIで表す、といった構造はバグを減らします。

一方で、過剰な抽象化はコストです。使われていない拡張点、薄いラッパー、目的のない関数ポインタ、過度に汎用化された `void *` は、読みやすさと追跡しやすさを落とします。

似たコードが並ぶ場合は、まず共通化を検討します。さらに、それらが並列の関係にあり、今後も同列に機能が増える見込みがある場合は、インターフェイスを固定した抽象化を検討します。

重要なのは、制約をコメントだけに頼らないことです。公開ヘッダ、未公開構造体、`static`、命名、所有権API、初期化/破棄関数の対といった構造で守れる制約を優先します。

## 修飾子

`static` は文脈により意味が変わります。ファイルスコープでは内部リンケージを与え、ブロックスコープでは静的記憶期間を与えます。

`extern` は他の翻訳単位に定義がある識別子を参照するために使います。グローバル変数の公開は結合度を高めるため、必要性を慎重に判断します。

`const` は読み取り専用として扱う意図を示します。関数が引数を変更しない場合に付けると、利用者とコンパイラの双方に意図が伝わります。

`volatile` は通常のメモリ同期手段ではありません。ハードウェアレジスタやシグナルなど、コンパイラ最適化を抑制する必要がある場面に限定します。

`_Atomic` はC11以降の原子操作に使います。スレッド間で共有する値に対して、データ競合を避けるための選択肢です。

## 標準ライブラリ

よく使う標準ヘッダには次のようなものがあります。

- `stdio.h`: 標準入出力、ファイル操作
- `stdlib.h`: 動的メモリ、変換、終了処理
- `string.h`: 文字列とメモリ操作
- `ctype.h`: 文字種判定
- `math.h`: 数学関数
- `wchar.h`: ワイド文字
- `assert.h`: アサート
- `errno.h`: エラー番号
- `threads.h`: C標準のスレッド機能

## POSIX API

Linux/POSIX環境では、標準Cライブラリに加えてPOSIX APIを使う場面があります。組み込み環境やESP-IDFでは同じAPIが使えるとは限らないため、POSIX依存の処理は明確に分離します。

- `fork`, `execvp`, `posix_spawn`: プロセス生成とプログラム実行
- `pipe`: パイプによるプロセス間通信
- `mmap`, `munmap`: メモリマップ
- `pthread_create`: POSIXスレッド
- `select`, `poll`: 複数ファイルディスクリプタの監視
- `opendir`, `readdir`, `closedir`: ディレクトリ操作

ファイルディスクリプタは、プロセスが開いているファイル、ソケット、パイプなどを表す整数です。通常、`0` は標準入力、`1` は標準出力、`2` は標準エラー出力です。

## 組み込み環境とESP-IDF

ESP-IDFでは、CコードがFreeRTOSタスク、ISR、ESP-IDFコンポーネント、各種ドライバAPIの上で動きます。通常のLinuxプログラムと違い、プロセス分離や十分な仮想メモリを前提にできません。

動的メモリは便利ですが、ヒープ不足や断片化の影響を受けます。長時間動作するファームウェアでは、確保と解放の頻度、確保サイズ、失敗時の復旧方法を設計に含める必要があります。

ISRでは、ブロッキングするAPIや通常タスク向けのAPIを呼べない場合があります。ESP-IDFやFreeRTOSにはISR用APIが用意されていることがあるため、呼び出し可能なコンテキストを確認します。

ログ出力もコストです。高頻度ログ、大きなログ、割り込みやタイミングに敏感な箇所でのログは、処理時間やメモリ使用量に影響します。ESP-IDFではログレベルとタグを使い、必要な情報を制御できる形にします。

ターゲット依存処理は小さく分離すると、ホスト環境でテストできるロジックを増やせます。GPIO、NVS、Wi-Fi、Bluetooth、タイマなどのESP-IDF依存処理と、純粋なデータ処理を分けることが保守性につながります。

## ライブラリ

静的ライブラリは通常 `ar` で作成し、拡張子は `.a` です。共有ライブラリは位置独立コードとして `-fPIC` でコンパイルし、`-shared` で生成します。Linuxでは拡張子 `.so` が一般的です。

共有ライブラリは実行時リンクの柔軟性がありますが、配布やABI互換性を考慮する必要があります。静的ライブラリは配布を単純にしやすい一方、成果物が大きくなることがあります。

## テストとデバッグ

小規模なCプログラムでは、標準ライブラリの `assert` を使った簡易テストでも効果があります。規模が大きくなった場合や継続的に保守する場合は、C向けのテストフレームワークを検討します。

GDBを使う場合は、`-g` を付けてビルドします。よく使う操作は次の通りです。

- `b file.c:123`: 指定行にブレークポイントを設定する。
- `b function_name`: 関数にブレークポイントを設定する。
- `run`: 実行する。
- `n`: 関数に入らず次の行へ進む。
- `s`: 関数に入って次へ進む。
- `c`: 次のブレークポイントまで続行する。
- `p value`: 変数の値を表示する。

メモリ管理を伴うコードでは、リーク、不正解放、範囲外アクセスを検出できる手段で確認することが重要です。
