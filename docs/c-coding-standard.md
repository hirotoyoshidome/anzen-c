# C言語コーディング規約

この文書は、C言語で安全かつ保守しやすいコードを書くための規約です。対象標準はC17を基本とし、GCC、Linux/POSIX環境、組み込み環境、ESP-IDFを使うプロジェクトを考慮します。

## 1. 基本方針

- 必須: 未定義動作、バッファオーバーフロー、メモリリーク、ダングリングポインタを避ける設計にする。
- 必須: 所有権、解放責務、エラー時の戻り値を関数単位で明確にする。
- 必須: コンパイラ警告を軽視しない。警告は原則として修正する。
- 必須: 対象プロジェクトの実行環境、ツールチェーン、メモリ制約、利用可能APIを明確にする。
- 推奨: 文字列処理、JSON、CSV、Webアプリケーションなど、アプリケーション層の複雑な処理にはC以外の選択肢も検討する。
- 推奨: パフォーマンス、メモリ配置、低レベル制御が重要な領域でCを採用する。

## 2. ビルドとコンパイル

- 必須: C17を基本とし、対象プロジェクトのC標準とコンパイラ設定を明記する。
- 推奨: GCCまたはESP-IDFのツールチェーンを前提にする場合は、その前提をビルド設定に反映する。
- 推奨: 開発時は少なくとも次の警告を有効にする。

```sh
gcc -std=c17 -Wall -Wextra -Wpedantic
```

- 推奨: デバッグ時は `-g` を付ける。
- 推奨: ヘッダ検索パスには `-I`、ライブラリ検索パスには `-L`、リンク対象には `-l` を使う。
- 必須: GCC固有機能を使う場合は、C標準ではなくGCC依存であることを明記する。
- 必須: ESP-IDF固有APIを使う場合は、標準CやPOSIXではなくESP-IDF依存であることを明記する。

## 3. ファイル構成

- 必須: 宣言はヘッダファイル、実装はソースファイルに分ける。
- 必須: ソースファイルを `#include` しない。
- 必須: ヘッダファイルにはインクルードガードを付ける。
- 推奨: ヘッダファイルには公開API、公開型、公開定数のみを置く。
- 推奨: そのソースファイル内でしか使わない関数やファイルスコープ変数には `static` を付ける。
- 禁止: 予約識別子と衝突しやすい、先頭アンダースコアの識別子を独自に定義しない。

## 4. インクルード

- 必須: 必要なヘッダを明示的にインクルードする。
- 推奨: 巨大な共通ヘッダに依存しすぎない。
- 推奨: 公開ヘッダでは、利用者に不要な依存を増やさない。
- 推奨: プロジェクト内ヘッダは `"..."`、標準ライブラリや外部ライブラリは `<...>` を使う。

## 5. 命名と記法

- 必須: 名前は役割が分かるものにする。
- 推奨: 関数名と変数名は小文字のスネークケースを使う。
- 推奨: 型名はプロジェクト内で一貫した規則にする。
- 推奨: ポインタ宣言では、`*` を変数名側に置く。

```c
int *value;
char *buffer;
```

- 禁止: 1つの宣言で複数のポインタ変数を宣言しない。

```c
/* 非推奨 */
int *a, b;
```

## 6. 型

- 必須: 配列の添字、要素数、容量、メモリサイズには原則として `size_t` を使う。
- 必須: 符号なしのビット演算では、意図した幅のunsigned型を使う。
- 推奨: 変更しない値には `const` を付ける。
- 推奨: 関数内で変更しないポインタ引数には `const` を付ける。
- 推奨: `struct` や `enum` は、読みやすさが上がる場合に `typedef` で型名を定義する。
- 必須: 整数型のサイズに依存する処理では、環境依存性を明示する。

## 7. 関数設計

- 必須: 関数は1つの責務に絞る。
- 必須: ポインタ引数を受け取る関数は、必要に応じて `NULL` を検査する。
- 必須: 関数がメモリを確保して返す場合、呼び出し側が解放するのか、専用の解放関数を使うのかを公開ヘッダに書く。
- 推奨: 成功時は `0`、失敗時は非ゼロを返す設計に統一する。
- 推奨: 不正な引数、I/Oエラー、メモリ不足など、失敗理由を区別できる戻り値またはエラー情報を用意する。
- 禁止: 呼び出し側が解放すべきメモリを、説明なしに返さない。

## 8. エラー処理

- 必須: `malloc`、`calloc`、`realloc` の戻り値は必ず確認する。
- 必須: ファイル操作、システムコール、POSIX APIの戻り値は必ず確認する。
- 推奨: 標準ライブラリやPOSIX APIの失敗理由が必要な場合は `errno` を扱う。
- 推奨: エラー時の後始末を統一し、確保済みリソースを漏らさない。
- 禁止: エラーを握りつぶして正常終了に見せない。

## 9. メモリ管理

- 必須: 動的に確保したメモリは、所有者を明確にする。
- 必須: `free` したポインタを再利用しない。
- 推奨: 呼び出し元のポインタは `free` 後に `NULL` を代入する。
- 必須: `realloc` は一時変数で受け、失敗時に元のポインタを失わないようにする。

```c
int *tmp = realloc(values, new_capacity * sizeof(*values));
if (tmp == NULL) {
    return 1;
}
values = tmp;
```

- 推奨: 動的配列は、要素数と容量を分けて管理する。
- 推奨: 容量拡張では、毎回1要素ずつ `realloc` せず、必要に応じて倍増などの方針を使う。
- 禁止: 関数内の自動変数のアドレスを戻り値として返さない。

## 10. 文字列

- 必須: C文字列は末尾のNUL文字を含めて領域を確保する。
- 必須: バッファサイズを超える書き込みをしない。
- 必須: 文字列長とバッファ容量を混同しない。
- 推奨: 文字列を受け取る関数では、可能な限りバッファサイズも引数で受け取る。
- 推奨: マルチバイト文字列を1バイト単位で文字として扱わない。
- 必須: `wchar_t` のサイズやエンコーディングは環境依存であるため、UTF-16固定として扱わない。

## 11. 配列とポインタ

- 必須: 配列の範囲外アクセスをしない。
- 必須: ポインタ演算は、対象の型に基づいて進むことを理解して使う。
- 推奨: 配列の終端を `NULL` で表す場合は、その設計を関数コメントや型で明示する。
- 必須: 一般の固定長配列には自動的な終端 `NULL` は存在しないことを前提にする。
- 推奨: 固定長配列は明示的に初期化する。

## 12. 構造体

- 必須: 構造体が所有するポインタメンバは、所有権と解放方法を明確にする。
- 推奨: 構造体の初期化関数と破棄関数を対にして用意する。
- 推奨: 可変長データを持つ構造体では、用途に応じてポインタ方式、固定長配列、フレキシブル配列メンバを選ぶ。
- 必須: ポインタ経由でメンバにアクセスする場合は `->`、実体からアクセスする場合は `.` を使う。

## 13. 修飾子とリンケージ

- 推奨: ファイル内に閉じる関数や変数には `static` を付ける。
- 推奨: 外部公開が必要な変数は原則として避け、必要な場合のみ `extern` 宣言を使う。
- 推奨: 関数的なマクロより、可能であれば `static inline` 関数を使う。
- 必須: `volatile` はハードウェアレジスタ、シグナル、割り込みなど、通常の最適化を避ける必要がある場面に限定する。
- 必須: `restrict` は別名参照がないことを保証できる場合にのみ使う。
- 非推奨: `register` は現代のコンパイラでは原則として使わない。

## 14. 抽象化設計

- 必須: 抽象化は、制約によって安全性を高めるために導入する。
- 必須: 抽象化したインターフェイスでは、所有権、初期化、破棄、エラー処理、呼び出し順序を明確にする。
- 推奨: 似たコードが並ぶ場合は、まず共通化によって重複を減らす。
- 推奨: 似たコードが並列の関係にあり、今後も同列に機能追加される可能性がある場合は、抽象化を導入してインターフェイスを固定する。
- 推奨: Cでは、公開ヘッダ、未公開構造体、`static` 関数、関数ポインタ、初期化/破棄関数の対によって抽象化を表現する。
- 推奨: カプセル化、ポリモーフィズム、所有権管理を構造として守れる設計にする。
- 禁止: 将来の可能性だけを理由に、使われていない抽象化を先に作らない。
- 禁止: コメントや命名だけに依存して制約を守らせない。

## 15. マクロと定数

- 推奨: 型を持つ定数には `const` または `enum` を使う。
- 推奨: 配列サイズ、条件コンパイル、コンパイル時設定にはマクロを使ってよい。
- 必須: 関数的マクロを使う場合は、引数の副作用と評価回数に注意する。
- 禁止: 複雑な処理をマクロに押し込まない。

## 16. スレッド、タスク、プロセス

- 必須: 複数スレッドから共有データへアクセスする場合は、同期方針を明確にする。
- 必須: スレッドセーフでない関数や共有状態を使う場合は、呼び出し側の責務を明記する。
- 必須: ESP-IDFやFreeRTOSのタスク間で共有データへアクセスする場合は、同期手段と所有権を明確にする。
- 必須: 割り込みコンテキストから呼び出す関数は、ISRで呼び出し可能なAPIだけを使う。
- 推奨: POSIX環境でプロセス間協調を行う場合は、パイプ、ソケット、共有メモリなどのIPCを明示的に設計する。
- 推奨: POSIXスレッドを使う場合は、C標準の `threads.h` との違いを理解して選択する。

## 17. 組み込み環境とESP-IDF

- 必須: 動的メモリを使う場合は、失敗時の動作、解放責務、断片化の影響を検討する。
- 必須: スタック使用量とヒープ使用量を意識し、大きな自動変数を不用意に置かない。
- 必須: ブロッキング処理、待ち時間、ログ出力はタスクや割り込みへの影響を考慮する。
- 必須: ESP-IDFのログ、NVS、Wi-Fi、Bluetooth、GPIO、タイマなどのAPIを使う場合は、初期化順序と呼び出し可能なコンテキストを確認する。
- 推奨: ターゲット依存処理は小さく分離し、上位ロジックへ直接広げない。
- 推奨: ホスト環境でテストできるロジックと、ESP-IDF依存部分を分ける。

## 18. ライブラリ

- 推奨: プロジェクト内の再利用コードは、ヘッダと実装を分けて小さなライブラリとして管理する。
- 推奨: 静的ライブラリは `ar` で作成し、拡張子は `.a` とする。
- 推奨: 共有ライブラリは `-fPIC` でコンパイルし、`-shared` で生成する。
- 推奨: 組み込み環境では、共有ライブラリを前提にせず、対象ビルドシステムのコンポーネントや静的リンクの扱いに従う。
- 必須: 公開する関数、型、定数と、内部実装を明確に分ける。

## 19. テストとデバッグ

- 必須: 主要な関数にはテストを用意する。
- 推奨: 小規模なコードでは `assert` を使った単純なテストを許容する。
- 推奨: 規模が大きい場合は、C向けのテストフレームワーク導入を検討する。
- 推奨: メモリ管理を伴うコードは、リークや不正アクセスを検出できる手段で確認する。
- 推奨: デバッグが必要な場合は `-g` を付けてビルドし、GDBなどを使う。
- 推奨: ESP-IDFプロジェクトでは、ホストで検証できるロジックとターゲット実機で確認すべき処理を分ける。

## 20. ログ

- 推奨: 障害調査に必要な箇所にはログを追加する。
- 必須: ライブラリコードでは、標準出力へ無条件にログを出さない。
- 推奨: 呼び出し側がログ出力の有無や出力先を制御できる設計にする。
- 必須: 組み込み環境では、ログ出力の頻度、サイズ、タイミングが処理時間やメモリに与える影響を考慮する。
- 推奨: ESP-IDFでは、プロジェクトのログ方針に従ってログレベルとタグを管理する。

## 21. 例外

この規約から外れる場合は、次のいずれかを満たす必要があります。

- 性能、互換性、プラットフォーム制約などの理由が明確である。
- コメント、設計文書、READMEなどで理由を説明している。
- レビューで合意されている。
